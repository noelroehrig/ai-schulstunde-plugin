# Plan 05: CI and server vendoring

Adds the GitHub workflows and the scripts they run: CI with `verify`, `verify:release`, and a
version-bump check, and the manual workflow that vendors a server release with a checksum and a tool
contract check (`SPEC.md` section 11.2). Read `SPEC.md` sections 11 and 12.2 and Appendix C first.
Plans 01 to 04 are done. This run may write `.github/`; `plugin/server/` stays protected.

Common rules for every phase:

- Scripts live in `scripts/` (CI helpers) and `checks/` (checks), as TypeScript run with `tsx`,
  with pure logic in their own functions and `node:test` tests next to them. Extend `tsconfig.json`
  and the `test` script to include `scripts/`.
- External programs (`git`, the server exe) are started with argument arrays (`execFile` or `spawn`
  without a shell), never with a command string. Every tag and ref from outside is validated
  against a strict pattern before use. Paths run on Windows too (`update-server.yml` runs on
  `windows-latest`, where `$RUNNER_TEMP` is like `D:\a\_temp`): a path argument is resolved and
  checked for existence and type, never matched against a POSIX-only pattern.
- Tests never touch the real `plugin/server/`, never reach the network, and never need the real
  exe. They use temporary directories and fakes.
- Workflows can't run in this container. Their structure is enforced by a check; their behavior on
  GitHub is verified by the maintainer after the first push.
- `npm run verify` passes at the end of every phase.

## Phase 1: version-bump check

Files: `checks/version-bump.ts`, `checks/version-bump-cli.ts`, and the test.

Acceptance criteria:

1. `checkVersionBump({ changedFiles, baseVersion, headVersion, changelogChanged })` returns no
   finding when no changed file is under `plugin/`. Otherwise it reports a finding when
   `headVersion` is not greater than `baseVersion` (numeric semver comparison of `X.Y.Z`) and one
   when `CHANGELOG.md` is unchanged.
2. `checks/version-bump-cli.ts --base <ref>` validates `<ref>` against
   `^[A-Za-z0-9._/-]+$` (no `..`, no leading `-`), reads the changed files with
   `git diff --name-only <ref>...HEAD` and the base version with `git show <ref>:plugin/.claude-plugin/plugin.json`,
   prints findings like the check runner, and exits 1 on a finding.
3. Script `check:version` runs the CLI.

## Phase 2: server vendoring and tool contract scripts

Files: `scripts/vendor-server.ts`, `scripts/tool-contract.ts`, `scripts/fixtures/fake-mcp-server.ts`,
and the tests.

Acceptance criteria:

1. `scripts/vendor-server.ts --tag <tag> --from <dir> [--root <repo>]` (`--root` defaults to the
   current directory; every path below is relative to it):
   - `<tag>` must match `^v\d+\.\d+\.\d+$`.
   - Reads `<dir>/onenote-mcp.exe` and `<dir>/onenote-mcp.exe.sha256` (one line,
     `<64 hex>  onenote-mcp.exe`); the SHA-256 of the exe (`node:crypto`) must equal it, otherwise
     it exits 1 without writing anything.
   - Writes `plugin/server/onenote-mcp.exe`, `plugin/server/onenote-mcp.exe.sha256`, and
     `plugin/server/VERSION` (the tag and a newline).
   - Raises the patch version in `plugin/.claude-plugin/plugin.json` (written back with two-space
     indentation and a final newline) and adds
     `## <new version> (<YYYY-MM-DD>)` with `- Server aktualisiert auf <tag>.` directly under
     `# Änderungen` in `CHANGELOG.md`.
   - The pure parts (tag check, checksum line parsing, version bump, changelog insertion) are tested
     on their own; one test runs the whole script against a temporary copy of a minimal repository.
2. `scripts/tool-contract.ts`:
   - `evaluateContract(toolNames)` requires `ping`, `get_notebooks`, `list_pages`, `get_page`,
     `create_page`, `replace_page`, and forbids `list_hierarchy_xml`, `get_page_xml`,
     `replace_page_xml`, `append_page_xml`; it returns one finding per missing or forbidden tool.
   - `listTools(command, args, env, timeoutMs)` starts the server without a shell and speaks MCP
     over stdio as newline-delimited JSON-RPC 2.0: `initialize` (protocol version `2025-06-18`,
     empty capabilities, client info `unterricht-tool-contract`), then the `notifications/initialized`
     notification, then `tools/list`, following `nextCursor` until the list is complete. It returns
     the tool names, stops the process in every case, and fails with a clear error on a timeout, an
     early exit, or an error response.
   - CLI `--exe <path>`: runs `listTools` with `ONENOTE_DISABLE_RAW_XML=1` in the environment, prints
     the tools and the findings, exits 1 on a finding.
   - `scripts/fixtures/fake-mcp-server.ts` answers `initialize` and `tools/list` with tool names from
     an environment variable and can be told to never answer. Tests start it with
     `process.execPath` and `--import tsx`, and cover a passing contract, a forbidden tool, a missing
     tool, pagination, and the timeout.

## Phase 3: workflows

Files: `.github/workflows/ci.yml`, `.github/workflows/update-server.yml`,
`checks/rules/workflows.ts`, and its test.

Acceptance criteria:

1. Every `uses:` pins a full commit SHA with the version as a comment. Use exactly
   `actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1` and
   `actions/setup-node@820762786026740c76f36085b0efc47a31fe5020 # v7.0.0`, with `node-version: 22`.
   No other actions.
2. `ci.yml` runs on every push and every pull request. Every job sets `permissions` (at most
   `contents: read`) and checks out with `persist-credentials: false`. Steps: setup-node, `npm ci`,
   `npm install -g @anthropic-ai/claude-code@2.1.288`, then:
   - job `verify` (always): `npm run verify`;
   - job `release` (only on a push to `main`): `npm run verify:release`;
   - job `version-bump` (only on pull requests, checkout with `fetch-depth: 0`):
     `npm run check:version -- --base "origin/$BASE_REF"`, with `BASE_REF` set from
     `github.base_ref` in the step's `env`.
3. `update-server.yml` runs only on `workflow_dispatch` with a required string input `tag`, on
   `windows-latest`, with `permissions: contents: write, pull-requests: write`, and `shell: bash`
   for every `run` step. Steps: checkout; setup-node; `npm ci`; the global Claude Code install as in
   `ci.yml`; `gh release download "$TAG" --repo noelroehrig/onenote-mcp --pattern onenote-mcp.exe --pattern onenote-mcp.exe.sha256 --dir "$RUNNER_TEMP/server"`;
   `npx tsx scripts/vendor-server.ts --tag "$TAG" --from "$RUNNER_TEMP/server"`;
   `npx tsx scripts/tool-contract.ts --exe plugin/server/onenote-mcp.exe`;
   `npm run verify:release`; then a commit on the branch `server/$TAG` as
   `github-actions[bot] <41898282+github-actions[bot]@users.noreply.github.com>`, a push, and
   `gh pr create` with a German title `Server $TAG` and a short German body. `TAG` comes from
   `inputs.tag` and `GH_TOKEN` from `github.token`, both through `env`.
4. Rule `workflows`, for every file in `.github/workflows/`: every `uses:` is pinned to a 40-character
   lowercase hex SHA followed by a `# v` comment; no `${{` appears inside a `run:` block (expressions
   only in `env:`, `with:`, `if:`, and `runs-on:`); every job or the workflow sets `permissions`.
   The rule works line by line on the simple YAML these workflows use; no YAML library.
5. `npm run verify` passes. The commit message body lists what the maintainer must check on GitHub:
   the first CI run (including whether `claude plugin validate` runs there without a login), the
   repository setting that allows GitHub Actions to create pull requests, and a first run of
   `update-server.yml` once `onenote-mcp` `v1.0.1` is released.
